# 6. За рамками MVP: защита от недобросовестных работодателей и интеграция с ATS

ТЗ ждёт здесь концепцию и архитектурный подход. Часть механизмов уже работает в MVP, они отмечены «реализовано».

## Защита от фиктивных вакансий и недобросовестных работодателей

### Угрозы

1. **Фиктивные вакансии:** сбор базы контактов, «завлекающие» вилки, мошенничество.
2. **Массовые нерелевантные рассылки.**
3. **Расхождение условий:** в приглашении одна вилка, на собеседовании другая.
4. **Компании-однодневки и чужие бренды.**

### Многоуровневая модель

| Уровень | Механизм | Статус |
|---|---|---|
| Данные кандидата | Контакты закрыты до согласия; точная сумма ожиданий не раскрывается никогда | реализовано |
| Частота | Квота 20 приглашений в неделю, обязательный персональный текст, одно активное приглашение на пару «компания–кандидат» | реализовано |
| Траст-скор | Контрольная сумма ИНН, совпадение домена почты и сайта, полнота профиля, возраст аккаунта, доля принятых приглашений, жалобы, аномальная вилка | реализовано (`trust.py`), виден кандидату |
| Аномалии | Вилка в 2,5 раза выше медианы рынка категории → сигнал «слишком хорошо, чтобы быть правдой» | реализовано |
| Обратная связь | Жалоба кандидата из приглашения: «фиктивная», «условия не совпали», «спам», «грубость» | реализовано, снижает траст-скор |
| Верификация юрлица | Запрос ЕГРЮЛ/ЕГРИП (ФНС, DaData): статус «действующая», дата регистрации, совпадение названия; подтверждение домена по DNS TXT или письмом на admin@ | концепция |
| Модерация по риску | Низкий траст-скор → приглашения и вакансии уходят в очередь модерации, лимит квоты снижается до 5; высокий — без модерации | концепция |
| Пост-фактум | Опрос кандидата через 2 недели после принятия: «условия совпали?» → вес в траст-скоре; повторные нарушения → блокировка | концепция |

Архитектура: `trust-service` подписан на события `invitation.*`, `complaint.created`, `vacancy.published` и
пересчитывает скор инкрементально. Внешние проверки (ФНС, DNS) выполняются асинхронно воркером. Результаты
кэшируются в `company_verifications`.

## Интеграция с ATS работодателей

Цель: работодатель живёт в своей ATS (Хантфлоу, Talantix, E-Staff, Potok), а платформа служит источником
подтверждённых кандидатов.

| Направление | Механизм | Статус |
|---|---|---|
| Платформа → ATS | Вебхуки `invitation.sent/accepted/declined`, `application.created` с подписью HMAC; при принятии — контакты и профиль кандидата | реализовано |
| ATS → платформа | REST API с токеном компании: потребности, вакансии, приглашения, статусы; OpenAPI позволяет сгенерировать клиента | API реализован, токены компании — концепция |
| Формат кандидата | Экспорт в JSON Resume / HR-XML + ссылка на PDF-профиль с QR-проверкой | PDF реализован, экспорт — концепция |
| Готовые коннекторы | Адаптеры для популярных ATS: маппинг этапов воронки ATS на статусы приглашений, двусторонняя синхронизация | концепция |
| SSO для HR | Вход сотрудников работодателя через корпоративный IdP (OIDC/SAML) на той же Keycloak-инфраструктуре | концепция |

Принцип: персональные данные уходят в ATS **только после согласия кандидата**, то есть после принятия приглашения
или собственного отклика. Это те же правила видимости, что и в интерфейсе.
