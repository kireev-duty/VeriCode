# 2. Механика тестирования кандидатов

## Задача и требования ТЗ

Нужно получить категорию (специализация × грейд) не из самоописания, а через опрос, выбор предполагаемого грейда и тест.
При этом:
1. единый набор заданий не подходит: задания быстро «разойдутся» по рынку;
2. генерация уникальных заданий нейросетью не гарантирует сопоставимой сложности и объективности;
3. грейд не понижается принудительно; смену грейда нужно ограничить по времени;
4. нужны регулярные короткие задания от работодателей.

## Решение: параметрические семейства + адаптивный тест (IRT/CAT)

### 1. Семейство заданий вместо задания

Семейство — это **шаблон** со стабильной структурой и случайной «поверхностью». Генератор получает случайное зерно
и подставляет данные, имена, константы и ветви логики. **Правильный ответ вычисляется**:
- исполнением сгенерированной программы — Python-семейства;
- SQL-движком — SQLite в памяти;
- точной моделью семантики: симулятор event loop JS, калькулятор специфичности CSS, модель фаз DOM-событий,
  формулы HPA, cron и umask.

Ответ никогда не пишется вручную и не придумывается LLM.

Пример: семейство `js_event_loop`, уровень 3. Каждый кандидат получает свою программу из `setTimeout`, промисов и
вложенных микрозадач. Ответ — порядок вывода, который вычисляет симулятор очередей.

| Свойство | Как достигается |
|---|---|
| Ответ нельзя «слить» | У кандидата свой экземпляр: медианная вероятность совпадения двух экземпляров — см. отчёт валидации, раздел 5 |
| Сопоставимая сложность | Структура семейства и уровня фиксирована, меняется только поверхность. У уровня свои параметры IRT |
| Объективность | Ответ вычисляется детерминированно; проверка нечувствительна к пробелам и виду кавычек |
| LLM не нужна для оценки | LLM (если подключена) можно использовать только для перефразирования условия; ответ проверяет генератор |

Банк: **59 семейств, 150 позиций** «семейство × уровень», 23 навыка, 5 специализаций (Backend, Frontend, Data/ML, QA,
DevOps). Форматы: предсказать вывод, найти нарушение контракта, оценить сложность алгоритма, посчитать (подсети,
мощности, HPA, cron), выбрать архитектурное решение по сценарию.

Банк расширялся по данным валидации. На 92 позициях тест из 18 заданий исчерпывал пул специализации: кандидат QA,
DevOps или Data видел почти все позиции своего пула. Добавлен 21 семейство для самых нагруженных навыков
(тест-дизайн, ML, статистика, Docker, Kubernetes, CI/CD, TypeScript, React, браузер, HTTP, SQL), а бедные шаблоны
расширены так, что вероятность совпадения экземпляров у **каждой** позиции ниже 1% (тест `test_families.py`).

### 2. Модель IRT 3PL

Вероятность верного ответа на позицию i:

P(θ) = cᵢ + (1 − cᵢ) / (1 + e^(−aᵢ(θ − bᵢ)))

Параметры:
- **bᵢ** — сложность;
- **aᵢ** — дискриминативность;
- **cᵢ** — вероятность угадать: 1/k для выбора из k вариантов, 0 для открытого ответа.

Начальные a и b задаёт эксперт по уровню семейства. По мере накопления ответов они калибруются: в
`item_family_stats` копятся экспозиции, ответы и доля верных.

### 3. Адаптивный отбор (CAT)

- **Оценка способности** — EAP по сетке из 161 точки с априорным N(0,1). Она устойчива на коротких тестах и при
  ответах «всё верно» / «всё неверно».
- **Следующее задание:**
  1. выбирается навык, который сильнее всего отстаёт от своей доли в **blueprint**;
  2. среди его позиций берётся максимум информации Фишера в текущей оценке θ;
  3. **контроль экспозиции** (онлайн-вариант Sympson–Hetter): позиция, показанная в доле r > 0,4 сессий *своей
     специализации*, допускается с вероятностью 0,4 / r. Доли берутся из БД (`service.exposure_rates`), первые
     50 сессий специализации контроль не действует. Если отсеялось всё — берётся исходный пул, сессия не встаёт;
  4. итоговая позиция выбирается случайно из топ-K по информации (randomesque), K сужается с 5 до 2 по мере
     уточнения оценки;
  5. не больше двух уровней одного семейства за попытку.

  Порог 0,4 подобран перебором (отчёт валидации, раздел 3): максимальная экспозиция позиции внутри специализации
  падает с ~94% до ~81% без потери точности. Ниже не опустить: квота навыка в blueprint задаёт минимум. Поэтому
  главная метрика — не экспозиция позиции, а произведение «экспозиция × вероятность совпадения экземпляра».
- **Blueprint** — доли навыков в тесте:
  - по умолчанию 70% — ядро специализации, 30% — заявленный стек кандидата;
  - для теста по вакансии 70% — навыки вакансии, 30% — ядро.

  Навык без заданий отображается на ближайший навык по графу сходства (например, `django` → `python`).
- **Остановка теста.** Тест заканчивается при любом из условий:
  - SD апостериорного распределения ≤ 0,33;
  - решение о грейде уже однозначно: P(≥ порога) ≤ 3% либо ≥ 97% при P(≥ следующего) ≤ 10%;
  - набрано 18 заданий.

  Минимум — 10 заданий. Обычно тест занимает 10–18 заданий.
- **Время:** у каждой позиции свой лимит (60–240 с) плюс 15 с допуска на сеть. Просроченный ответ засчитывается как
  неверный.

### 4. От θ к грейду

Пороги на шкале θ (популяция N(0,1)): Junior ≥ −0,9, Middle ≥ 0,1, Senior ≥ 1,1, ниже — Intern.

| Итог попытки | Условие | Что происходит |
|---|---|---|
| `confirmed` | P(θ ≥ порог заявленного) ≥ 0,6 | Категория присвоена |
| `upgrade_available` | И P(θ ≥ порог следующего) ≥ 0,6 | Категория присвоена, тест на грейд выше открыт 7 дней |
| `not_confirmed` | Иначе | Грейд **не понижается**: прежний сохраняется, сразу доступен тест на грейд ниже |

Порог 0,6 выбран на симуляции: он балансирует точность и долю завышений, подробности в отчёте валидации.

**Заявленный грейд не влияет на оценку.** Он задаёт только стартовую точку отбора заданий. Априорное распределение
одинаковое для всех, поэтому «заявить Senior на удачу» бесполезно. Это проверено в валидации.

### 5. Политика частоты

| Правило | Значение |
|---|---|
| Тест на грейд ниже после неудачи | Сразу |
| Повтор того же грейда после неудачи | Через 30 дней |
| Подтверждение текущего грейда (обновить результат) | Раз в 30 дней |
| Смена подтверждённого грейда (вверх или вниз) | Не чаще раза в 90 дней |
| Исключение | После `upgrade_available` тест на грейд выше доступен 7 дней |

Ограничения проверяет сервер (`GET /api/assessment/eligibility`). Интерфейс показывает причину и дату, с которой
попытка станет доступна.

Почему так:
- **Провал не сжигает попытку.** Тест на ступень ниже доступен сразу: кандидат не должен выпадать из оборота из-за
  завышенной самооценки. Прежний подтверждённый грейд при провале сохраняется.
- **Повышение — только отдельным тестом.** Автоматического прыжка Junior → Middle нет: уверенный результат
  открывает тест на ступень выше на 7 дней, и грейд меняется, только если этот тест его подтвердит.
- **Нельзя скакать по грейдам.** Подтверждённый грейд меняется не чаще раза в 90 дней, повтор того же грейда —
  через 30 дней. Иначе грейд превращается в лотерею, а работодатель видит сегодня Senior, завтра Middle.
- **Повторная попытка — всегда новые экземпляры заданий.** Семейства параметрические, поэтому запоминание
  ответов прошлой попытки не помогает.

Пока ни один грейд не подтверждён, кандидат остаётся в выдаче работодателя с пометкой «заявлен X · не
подтверждён», ниже всех подтверждённых кандидатов (см. механику подбора).

### Экспресс-режим для проверки жюри

Вход «Новый кандидат» на странице входа (`POST /api/auth/demo-login?role=candidate_new`) каждый раз создаёт
новый одноразовый аккаунт. Каждый эксперт проходит опрос и тест сам и не упирается в ограничения частоты
чужих попыток. Для демо-аккаунтов тест короче: 6–10 заданий вместо 10–18, это 3–5 минут. Алгоритм тот же, но
останов наступает раньше, поэтому погрешность θ выше. Точность в отчёте валидации измерена на обычном режиме.

### 6. Защита целостности

Защита многоуровневая:
1. **Параметризация:** слитый ответ бесполезен.
2. **Большой пул + контроль экспозиции + лимит семейства:** у кандидатов разные наборы позиций.
3. **Детектор утечек.** По каждой позиции считается CUSUM остатков «наблюдаемая − ожидаемая» доля верных ответов
   при оценённой способности отвечающих: S ← max(0, S + (xᵢ − P(θ̂ᵢ)) − 0,15). При S > 3 и не менее 20 ответах позиция
   получает статус `flagged` и выходит из ротации до проверки. Если семейство «раскусили» (появился разбор, как решать),
   оно уходит из ротации, а автор добавляет новую поверхность или уровень.
4. **Сигналы:** время ответа, вставка из буфера, уход со вкладки, копирование. Они фиксируются в отчёте сессии
   (`flags`), но **не штрафуют автоматически**: ложные срабатывания недопустимы.
5. **До конца теста** кандидат не видит правильность ответов: ответ на одно задание не подсказывает следующие.
6. **Жалоба на задание.** В разборе после теста у каждого задания есть кнопка «Задание некорректно» (причина и
   комментарий в `AssessmentItem.signals.report`). Жалобы попадают в выгрузку пилота и в отчёт валидации.

### 7. Пилот на людях

После теста кандидат может заполнить необязательную анкету: стаж, должность, самооценка, грейд по оценке тимлида
(`POST /api/assessment/sessions/{id}/survey`). Обезличенная выгрузка (`GET /api/assessment/pilot/export`, заголовок
`X-Pilot-Token` = `PILOT_EXPORT_TOKEN`) обрабатывается `validation/pilot.py`: согласие θ̂ со стажем и оценкой
тимлида (ρ Спирмена, каппа), калибровка позиций (наблюдаемая и ожидаемая доля верных), время, жалобы.

### 8. Тест по вакансии

`POST /api/assessment/blueprint-preview` и `POST /api/assessment/sessions` с `vacancy_id`: навыки вакансии
(обязательные с весом 1, «будет плюсом» с весом 0,4) формируют blueprint. На странице «Как это работает» можно
вставить текст вакансии и увидеть, как меняется состав теста и какие экземпляры получит кандидат. Повторная
генерация даёт новые экземпляры той же сложности.

### 9. Регулярные задания

Раз в неделю кандидат с подтверждённым грейдом получает короткую задачу от работодателя своей специализации: решить
или предложить подход. Задачи подбираются с учётом стека кандидата. Ответ оценивается по прозрачной рубрике:
ключевые пункты с маркерами, кандидат видит, какие пункты он раскрыл. Задача может прийти и как «челлендж» внутри
приглашения.

Маркеры не ловят ответ, написанный своими словами. Если подключена языковая модель, она решает по каждому пункту
рубрики, раскрыт ли он по смыслу, и обязана привести цитату из ответа. Пункт засчитывается, только если цитата
действительно есть в тексте ответа. Итоговый балл считает код по весам рубрики, а не модель.

Результат обновляет индекс актуальности профиля: он входит в ранжирование и виден работодателю
(«подтверждён активностью N дней назад»).

## Опрос

Шаги:
1. Согласия.
2. Специализация и отрасли.
3. Стек с годами, общий опыт, формат, роли.
4. Три вопроса самооценки: самостоятельность, масштаб решений, роль в код-ревью.
5. Выбор предполагаемого грейда.

Система подсказывает грейд по ответам и опыту, но решение за кандидатом. Ответы опроса сохраняются в истории и
**не влияют на категорию**: её определяет только тест.
